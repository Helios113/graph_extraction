# Series 3 findings: Hugging Face transformers

See [test_plan.md](../../test_plan.md). Code: `tests/series3/run_series3.py`, configs in `tests/series3/configs/` (generated by `construct/make_config.py`), run on ruapehu H100 (ORT CUDA EP, fp32, TF32 off; job 61954) via `tests/series3/run.sh`. The earlier CPU-EP run is kept in [../series3_cpu/](../series3_cpu/FINDINGS.md). Input: random token ids, batch 2, sequence 8. Baseline: torch hooks / autograd on the HF model itself (boundary values and logits for the forward checks; gradients through an injected layer input).

Boundaries: h0 = embeddings, h(2l+1) = post-attention of layer l, h(2l+2) = post-MLP. Spans checked per model: h0->h1, h1->h2 (single sublayers), h0->h2 (one layer), h2->h4, last layer, h0->h6 (three layers). Pullbacks for all four loss types (`JacobianExtractorLoss` and the three adversarial losses) on every span; mid-layer spans are forward-only for the torch gradient comparison (no injectable torch boundary), the layer-aligned ones are compared against torch autograd. `JacobianExtractorLoss` is the Jacobian extractor (linear, no minimum), so it is not optimised: it is used to extract the **full last-token Jacobian** d out[last token, :] / d input (d_model one-hot pullback calls) on every layer-aligned span and compared with torch autograd rows. The 30-step SGD / AdamW trajectory (three adversarial losses) is run on the multi-layer span.

Criteria: static checks (extraction, loss, gradient) < 1e-4 (deep fp32; series 1 used 1e-5), Jacobian < 1e-4, trajectories < 1e-3 measured as max |L_ORT − L_torch| / max |L_torch| over the 30 steps (the quantity plotted).

## Conclusion

- **Forward, extraction, pullback loss, gradient and the full last-token Jacobian pass** the criteria for all five models, all four loss types and all spans (largest: 1.1e-5 gradient and 6.9e-6 Jacobian on qwen2.5-0.5b, 3.1e-6 extraction on opt-125m). Full-model ORT logits match torch to <= 2.2e-4 absolute on logits of size 15–105.
- **Optimisation**: all 30 model x adversarial-loss x optimiser trajectories are below the 1e-3 criterion (worst: smollm2 8.5e-4 and opt-125m 5.6e-4, both SquaredDiff + SGD). AdamW agrees to <= 1.9e-6 everywhere.

## Findings and caveats

- **Two SquaredDiff + SGD trajectories are close to the criterion.** On the per-step relative metric stored in `results.json` (`max_rel_traj_diff`, |ΔL| / |L_torch| at each step, stricter than the plotted one) they exceed 1e-3: opt-125m 1.4e-3 and smollm2-135m 1.6e-3 (all others <= 1.9e-4). This was not seen in the earlier CPU-EP run (<= 2.2e-4 on the same metric), so it is probably GPU-vs-CPU kernel differences amplified by 30 plain-SGD steps. Not diagnosed (not tested in float64).
- **`JacobianExtractorLoss` (formerly `MaskedSumLoss`) is no longer optimised.** The earlier CPU run optimised it and found four SGD trajectory misses (tinystories 6.6e-2, gpt2 2.8e-3, smollm2 2.0e-3, opt 1.2e-3); these came from the loss being linear with no minimum (SGD runs it to -2e5 and so amplifies fp32 gradient differences), not from a gradient error, and are recorded in the CPU findings only.
- **No transformer with control flow was tested.** The plan asks for models "with and without control flow"; all five exported graphs contain no `If`/`Loop`/`Scan` (`control_flow: false` in every `results.json`), so only the without-control-flow half is covered. Given series 2 (If/Loop break extraction and pullback), a transformer export that does contain them would be the next test.
- **Export path**: models are exported with the project's own `construct.model_export` (`torch.onnx.export`) through `ensure_base_model`, not through `optimum`. The KV-cache series (4, 5) does use optimum.
- Only the mid-layer spans h0->h1 and h1->h2 lack a torch gradient comparison (forward and pullback construction only); all layer-aligned spans, including h0->h6, are compared against torch autograd.
